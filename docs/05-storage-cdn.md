# 05 — Storage and CDN

> Where the audio files live, how they get to listeners, and the failure modes that bite hardest.

---

## The two-bucket pattern

There are two fundamentally different kinds of audio in DescribeAT, and they should never share a bucket:

| Bucket | What's in it | Who reads it | Access pattern |
|--------|--------------|--------------|----------------|
| **Public** | AD track audio (the narration played to listeners), poster images | Listeners (the world) | Read-heavy, cacheable, low-latency |
| **Private** | Reference audio (the original movie/TV audio, used to generate fingerprints), admin uploads in progress | Fingerprinter service, admin users | Read-rare, write-occasional, signed URLs only |

**Why two:** Reference audio and AD track audio have different access patterns, different licensing implications, and different security profiles. Reference audio may have copyright restrictions that AD track audio does not. Mixing them is a security and licensing risk.

**Why not one bucket with prefixes:** It works in theory, but in practice a future contributor will accidentally make the prefix world-readable. The blast radius of "I made the private prefix public" is the entire content library. Two buckets forces the security boundary to be explicit at the infrastructure level.

---

## Public bucket

### Contents

- **AD track audio** (one object per AD Track record). Format: MP3 or AAC. Bitrate: 128-192 kbps is fine for narration. File size: typically 5-50 MB per track.
- **Poster images** (one or more per Title). Format: JPEG or WebP. Resolution: 800x1200 is good for mobile. File size: 200-500 KB.

### Access

- World-readable via CDN
- Direct bucket access blocked at the account level (only the CDN can read)
- Bucket policy: deny all access except from the CDN's service principal

### URL pattern

```
https://{cdn-domain}/media/ad-tracks/{trackId}.mp3
https://{cdn-domain}/media/posters/{titleId}/{imageId}.jpg
```

The path prefix `/media/` distinguishes content URLs from app URLs (`/app/*` is the PWA, `/api/*` is the data layer, `/t2s/*` is the fingerprinting engine).

### Caching rules

| Path | TTL | Notes |
|------|-----|-------|
| `/media/ad-tracks/*.mp3` | 30 days | Range-request friendly. Audio files are immutable per track. |
| `/media/posters/*` | 30 days | Cache-bust by including a version query param when updating. |
| `/app/*` (hashed bundles) | 1 year | Immutable. |
| `/app/index.html` | 5 minutes | Must-revalidate. |

**Range requests:** AD track files are large enough that listeners may want to seek. Make sure your CDN supports HTTP Range requests for `/media/ad-tracks/*`. Without this, listeners have to download the entire track before they can play it.

### Anti-pattern — caching opaque responses

A common silent failure: your CDN caches responses that don't have a real HTTP status. Specifically, if your storage backend returns an opaque response (status 0, no real body) under any condition, and the CDN caches it as a 200, listeners will get a corrupted audio file. Playback fails silently with no error message.

**Fix:** Set `statuses: [200]` on your cache rules. Never `[0, 200]`. Always validate that the upstream response has a real HTTP status before caching.

This bit the original production deployment in 2026 and is a common silent-failure trap. See [`workflows/incident-response.md`](../workflows/incident-response.md) for the full diagnostic recipe.

## Private bucket

### Contents

- **Reference audio** (one object per Title). Format: WAV or FLAC, since lossy codecs degrade fingerprint quality. Sample rate: 44.1 kHz or 48 kHz. File size: 50-500 MB per title.
- **Admin upload staging** (temporary, deleted after processing). Used when an admin uploads an AD track — the file lands here first, gets fingerprinted, then gets moved to the public bucket.

### Access

- Not public. Period.
- Access only via signed URLs with a short TTL (5-15 minutes)
- Signed URLs are generated by the data layer when needed (e.g. when the fingerprinter needs to download a reference audio)
- Direct bucket access blocked at the account level

### Lifecycle

- Reference audio: stored indefinitely. If a Title is deleted, its reference audio is deleted too.
- Admin upload staging: deleted within 24 hours of successful processing, or on failure.

## CDN configuration

### What to choose

The most common choices:

| CDN | Strengths | Weaknesses |
|-----|-----------|------------|
| **AWS CloudFront** | Tight integration with S3, Lambda@Edge for custom logic | Cold start on Lambda@Edge functions, expensive for low-traffic sites |
| **Cloudflare** | Free tier is generous, fast globally, good DDoS protection | Less tight integration with non-AWS origins |
| **Fastly** | Excellent edge compute, VCL is powerful | More complex setup, no free tier |

For most self-hosters, **Cloudflare** is the easiest starting point. The free tier covers a small deployment, and the global edge network is fast.

### The routing rules

| Path pattern | Route to | Cache? |
|--------------|----------|--------|
| `/t2s/*` | Fingerprinting engine | No (POST, dynamic) |
| `/api/*` | Data layer (GraphQL) | No (per-user responses) |
| `/media/ad-tracks/*` | Public bucket | Yes (30 days) |
| `/media/posters/*` | Public bucket | Yes (30 days) |
| `/app/assets/*` | Public bucket (PWA bundles) | Yes (1 year) |
| `/app/*` | Public bucket (PWA HTML) | Yes (5 min, must-revalidate) |
| `/*` | Default to PWA | No |

### Origin configuration

The CDN needs to know where each route's origin is. For a single-region deployment:

```
/t2s/*    →  https://matcher.{your-domain}/  (internal)
/api/*    →  https://datalayer.{your-domain}/  (internal)
/media/*  →  https://{bucket}.s3.{region}.amazonaws.com/
/app/*    →  https://{bucket}.s3.{region}.amazonaws.com/
```

**The CDN's origin connections should be authenticated** (signed requests, mTLS, or VPC-internal). Don't expose the data layer to the public internet just because the CDN is in front of it.

### Custom error pages

When the origin returns 4xx or 5xx, the CDN should serve a custom error page (HTML for the PWA, JSON for the API). For the PWA, this means showing the user a "Something went wrong" UI rather than the CDN's default error page.

For the API, return JSON:

```json
{
  "error": "NOT_FOUND",
  "message": "The requested resource does not exist"
}
```

This way, the app can parse the error and surface a user-friendly message.

## Pre-signed URLs

For private content (admin uploads, reference audio), the app or admin portal needs a pre-signed URL that grants temporary access.

### Generating a pre-signed URL

Most S3-compatible SDKs have a built-in method:

```python
# Python (boto3)
url = s3_client.generate_presigned_url(
    'get_object',
    Params={'Bucket': 'private-bucket', 'Key': 'reference-audio/abc123.wav'},
    ExpiresIn=300  # 5 minutes
)
```

```javascript
// JavaScript (AWS SDK v3)
const command = new GetObjectCommand({ Bucket: 'private-bucket', Key: 'reference-audio/abc123.wav' });
const url = await getSignedUrl(s3Client, command, { expiresIn: 300 });
```

### Using a pre-signed URL

The client uses the URL as if it were a normal HTTP GET. The signature is in the query string; the storage service validates it and serves the object.

### Pitfall — signing on the wrong bucket

A common bug: the data layer signs URLs for the wrong bucket (e.g. signing for the public bucket when it meant the private bucket). The result: 403 Forbidden errors, or worse, unauthenticated access to private content.

**Fix:** Centralize pre-signed URL generation in one place in your data layer. Audit it before deploying.

## Anti-patterns

### 1. Storing the AD track audio in the private bucket "for security"

A common over-reaction: "What if someone downloads all our AD tracks?" The answer: the AD tracks are the *content* — listeners are supposed to download them. They go in the public bucket. The reference audio is the *internal source material* — that goes in the private bucket.

### 2. Letting the data layer proxy audio files

If your data layer fetches the audio from storage and serves it to the client, you've added an unnecessary hop. The data layer is for metadata, not for binary content. The CDN should serve audio directly from the bucket.

### 3. Using the same CDN for the API and the static content

CDN caching rules for static content (long TTL, immutable) and API responses (no cache, per-user) are fundamentally different. If you use the same CDN with a single set of rules, you'll either over-cache API responses (security hole) or under-cache static content (slow). Use different CDN distributions or different routing rules.

### 4. Forgetting to invalidate the CDN when content changes

When you update a poster image, the CDN may still serve the old version for up to 30 days. Two fixes:

- **Cache-bust by URL:** include a version query param (e.g. `poster.jpg?v=2`). Bump the version on every update.
- **CDN invalidation:** call the CDN's API to invalidate the specific URL. Adds complexity but works.

### 5. CORS misconfiguration

If the PWA and the API are on different origins, you need CORS to be configured correctly. The CDN's CORS policy should:

- Allow the PWA's origin (not `*` for credentialed requests)
- Allow the headers your app actually uses (typically `Authorization`, `Content-Type`)
- Allow the methods your app actually uses (typically `GET`, `POST`, `OPTIONS`)

**The most common CORS bug:** allowing `*` for `Access-Control-Allow-Origin` while also allowing credentials. Browsers reject this combination. Use the specific origin, not `*`.

## Backup and disaster recovery

### What to back up

- **All buckets** (public and private). The audio content is the most expensive thing to recreate.
- **The hash database.** Re-fingerprinting is cheap (~$0.50 per track) but takes time. Back up the database, not just the audio.
- **The data layer's database.** The metadata is cheap to recreate, but you don't want to.

### How often

- **Daily backups** for the audio buckets and data layer.
- **Continuous replication** for the data layer (if your cloud provider supports it).
- **Test restores** monthly. Backups you've never restored from are not backups.

### RPO and RTO targets

| Tier | RPO (data loss) | RTO (recovery time) |
|------|-----------------|---------------------|
| Public audio | 24 hours | 4 hours |
| Private reference audio | 24 hours | 4 hours |
| Hash database | 1 hour | 1 hour |
| Data layer metadata | 5 minutes | 30 minutes |

These are the original production targets. Adjust to your own needs.

## What to monitor

- **Bucket size over time.** Should grow roughly linearly with new content. Sudden drops = accidental deletion.
- **CDN cache hit rate.** Should be >90% for the public bucket. Low cache hit rate = misconfiguration.
- **CDN error rate.** 4xx and 5xx responses from the CDN. Spikes = content missing or origin errors.
- **Origin latency.** How long the CDN waits for the bucket to respond. Spikes = bucket throttling.
- **Egress bandwidth.** How much data leaves the bucket. Should match listener usage patterns.

## Self-hosting checklist

- [ ] Two buckets: one public, one private
- [ ] Public bucket is only readable from the CDN
- [ ] Private bucket is only readable via signed URLs
- [ ] CDN routes `/t2s/*`, `/api/*`, `/media/*`, `/app/*` to the correct origins
- [ ] Caching rules are correct (immutable for hashed assets, range-friendly for audio)
- [ ] CORS is configured for the PWA's origin
- [ ] Pre-signed URL generation is centralized
- [ ] Backups are running and tested
- [ ] Monitoring is set up
- [ ] You have a runbook for "the audio bucket is empty / corrupted"
